# SQLite Eval DB — Integration Notes

Added 2026-05-29. Status: **Phase 1 (read-only consumption from chess-book-editor) shipped**.

> **TL;DR for AI agents picking this up:** there is now a `output/positions.db` SQLite file that mirrors `positions*.js` + `chessdb_cache.json`. The sibling repo [chess-book-editor](../chess-book-editor/) consumes it read-only via Flask. This repo's render / verify / enrich pipelines **still read the .js files as before**; the .db is regenerated from them after each `render_site.py` run if you choose to. No production code in this repo changed.

## Why this exists

The editor (`chess-book-editor`) wants to surface engine evals + chessdb winrates next to the moves it's editing, plus trap/brilliant markers in its move list. Two options were on the table:

1. Editor reads `output/site/positions_view.js` directly (47 MB, all in memory).
2. Editor queries a SQLite file with `WHERE fen = ?` — O(1) lookups, multi-process safe, supports analytical queries.

We took (2) because it scales better and unlocks future moves (Phase 2 = pipeline migration; Phase 3 = sql.js-httpvfs on the static site, deferred until measured pain).

## Schema

Two tables, long-format (`(fen, depth)` composite key) so adding depth 36/40 later is zero schema change:

```sql
CREATE TABLE evals (
  fen        TEXT NOT NULL,
  depth      INTEGER NOT NULL,    -- 12 | 22 | 28 | 32 | ...
  score      INTEGER,             -- mover-POV centipawns
  mate       INTEGER,             -- mover-POV plies-to-mate, sign matches score side
  best_iccs  TEXT,                -- engine's recommended move
  pv_json    TEXT,                -- JSON array of ICCS strings
  PRIMARY KEY (fen, depth)
) WITHOUT ROWID;
CREATE INDEX evals_by_depth ON evals(depth);

CREATE TABLE chessdb (
  fen        TEXT PRIMARY KEY,
  status     TEXT,                -- "ok" / "unknown" / etc, mirrors chessdb.cn response
  moves_json TEXT                 -- JSON array of {iccs, score, rank, note, winrate}
) WITHOUT ROWID;
```

WAL mode is **persisted** via the migration script (`journal_mode=WAL`). This is the load-bearing decision: it lets the editor read while `verify_traps` / `enrich_decisive` write, with no lock contention. Don't toggle it off.

### What's intentionally NOT in the DB

- **`best_chinese` / `pv_detail`** — these are derived in [`render_site.py`](site_builder/render_site.py) via cchess `to_text()` from `best_iccs` / `pv`. The consumer (editor) re-derives them on demand using its own cchess. Storing them would create a cache-coherence problem with no upside.
- **trap / brilliant flags** — also derived (server-side in `render_site.py:compute_game_stats`, in-browser in the editor's `plyVerdict`). Same reason: thresholds may shift; recompute from raw scores.

## Cross-project FEN format — verified byte-identical

This was the make-or-break gate. Both sides emit the **same** FEN shape: `<board> <w|b>` (no halfmove clock, no fullmove number).

- Python side: `cchess.board.ChessBoard.to_fen()` ([board.py:744](https://github.com/walker8088/cchess/blob/master/cchess/board.py)) — board + space + `"w"` or `"b"`.
- JS side (editor): `applyIccs()` in [board.js](../chess-book-editor/frontend/assets/board.js) — `${newPos} ${side === "w" ? "b" : "w"}`.

Empirically confirmed: editor walks the tree of a real XQF, derives every node's FEN via `applyIccs`, batch-queries this DB. **92.7% depth-12 hit rate across 6 files / 3180 FENs**. The 7.3% gap is `_dedupe_by_name` in `build_data.py` skipping case-duplicate XQFs — i.e. real coverage, not encoding mismatch. d22 / d28 / d32 / cdb hit rates also match expected pipeline behaviour (SKIP_OPENING_PLIES, `|score|>300` enrichment band, selective d28/d32 sweeps).

## Performance (vs current `<script src="positions.js">` flow)

Benchmarked by [`site_builder/bench_sqlite.py`](site_builder/bench_sqlite.py) (full data):

| operation | SQLite | current JS flow |
|---|---|---|
| single FEN, cold | 5.6 ms | 108 ms (parse cost) |
| all depths for one FEN | 0.04 ms | needs 4 files in memory |
| 100 sequential SELECTs | 0.9 ms total | (free after parse) |
| `WHERE fen IN (100)` | 0.5 ms | n/a |
| "FENs at d=22 but missing d=28" (verify_traps resume) | 9.7 ms | seconds in Python |
| top-10 d12→d28 score swings | 37 ms | seconds in Python |

For the editor's batch-on-file-open workflow (~100-500 FENs per XQF), the .db lookups complete in 1-5 ms, vs ~108 ms just to parse the JS module.

## What the consumer (chess-book-editor) does

Strictly read-only. The editor:

1. On boot: `GET /api/eval/info` → reports DB path + rows-per-depth to the UI for graceful degradation.
2. On XQF load: walks the whole move tree from `init_fen` via `applyIccs`, collects all FENs, POSTs them to `/api/eval/batch`.
3. The result is stashed in `EDITOR.evalsByFen` and rendered as:
   - A summary strip below the board showing the active ply's evals.
   - **⚠** badges + amber row-tint on trap plies, **✨** badges + violet row-tint on brilliant plies, computed in the browser using the same thresholds as `render_site.py:compute_game_stats` / `_compute_brilliants`.

The editor's source-of-truth path resolution:
- Default: `<editor_repo>/../chess-book-ai/output/positions.db` (i.e. sibling repos).
- Override: `preferences.json` key `evalDbPath`.

The editor never opens this file for write — it uses SQLite URI mode `?mode=ro`. If the file is missing, the editor degrades to "引擎資料未連線" silently.

## Score sign convention — DB is mover-POV, UI must flip to red-POV

**The DB stores `score` and `mate` from the *side-to-move's* perspective**, mirroring Pikafish UCI output verbatim (positive = side-to-move is winning). That's the raw engine output, no transformation at write time.

**But every UI surface in chess-book-editor displays red-perspective scores** (positive = red advantage, negative = black). chess-book-ai's site_builder does the same (`board.js:redPerspectiveScore`). For consistency the editor MUST apply the flip at the display boundary.

### The rule

```python
def to_red_score(fen: str, score: int | None) -> int | None:
    """DB stores mover-POV; flip to fixed red-POV for display.
    Red-to-move (FEN ends `w`): keep as-is.
    Black-to-move (FEN ends `b`): flip sign."""
    if score is None:
        return None
    return score if fen.split()[1] == 'w' else -score


def to_red_mate(fen: str, mate: int | None) -> int | None:
    """Same flip for mate distance (positive = side-to-move mates in N)."""
    if mate is None:
        return None
    return mate if fen.split()[1] == 'w' else -mate
```

JavaScript equivalent (for the frontend that reads `/api/eval/batch` JSON):

```js
function toRedScore(fen, score) {
  if (score == null) return null;
  return fen.split(' ')[1] === 'w' ? score : -score;
}
function toRedMate(fen, mate) {
  if (mate == null) return null;
  return fen.split(' ')[1] === 'w' ? mate : -mate;
}
```

### Where to apply

- ✅ **Every place a score/mate is rendered for a human** — the strip below the board, hover tooltips, badge labels.
- ✅ Both `score` and `mate`. PV's leading sign in some display formats also needs flipping if you derive it from `score`.
- ❌ `best_iccs`, `pv_json` — ICCS notation is absolute board coordinates, no flip needed.
- ❌ **Trap / brilliant detection** — the `_ply_loss` formula already operates in mover-POV (`score(fen_before) + score(fen_after)` is the mover's giveaway). Flipping inside detection would invert sign meaning and break threshold checks. Run detection on the raw DB values, then apply the display flip only when surfacing the resulting badges' numeric labels.
- ❌ Server-side aggregations (averages, totals over groups of FENs) — those have no inherent "perspective" until projected onto one side.

### Cross-check

A position with FEN ending `b` and DB `score = -344` should display as `+344` (Red advantage). The editor's existing screenshot at `127.0.0.1:5174` was showing `-31` for a black-to-move FEN; with the flip it should read `+31`.

## Trap / brilliant detection — single source of truth

The editor ports these constants from [`render_site.py`](site_builder/render_site.py) verbatim:

```js
const SKIP_OPENING_PLIES = 15;   // skip plies 1..15
const TRAP_SHALLOW_MAX   = 50;
const TRAP_DEEP_MIN      = 100;
const TRAP_DEEP_MAX      = 2000;
const BRILLIANT_MIN      = 50;
const BRILLIANT_MAX      = 300;
```

**If you change these in `render_site.py`, also update `chess-book-editor/frontend/assets/editor.js`** — the comment block above `plyVerdict` calls this out. There is also `chess-book-editor/backend/test_trap_spotcheck.py` which runs the same logic on real XQF files and prints trap counts — useful as a sanity check after changes.

The `_ply_loss` formula (`score(fen_before) + score(fen_after)`, both POV-relative) is also identical between the two repos.

## Phase 2 (future) — pipeline migration

When master decides to pull the trigger, the order to migrate the writers is:

1. **`chessdb_query.py`** — easiest, single table, no concurrency.
2. **`build_data.py`** — depth-12 writer; biggest table; rebuild from XQF library.
3. **`enrich_decisive.py`** — depth-22 writer; resume logic becomes `WHERE depth=22 AND fen NOT IN (SELECT fen FROM evals WHERE depth >= 22)`, much cleaner than the current manual checkpoint.
4. **`verify_traps.py`** — depth-28 writer; same resume-query pattern.
5. **`render_site.py`** — switch to reading from DB; keep the existing `positions_view.js` export step so the static site is unaffected.

At that point `migrate_to_sqlite.py` becomes a one-time bootstrap rather than something to re-run after every build.

## Phase 3 (future) — static site on SQLite

Deferred. The cost/benefit analysis (sql.js-httpvfs vs current 47 MB `<script>`) depends on real wire-size and TTI measurements that haven't been taken yet. Before doing this, measure:

- Actual gzipped size of `positions_view.js` on the GitHub Pages CDN (probably 5-10 MB).
- Time-to-interactive on a cold visit, especially on mobile.
- Whether the `file://` browse capability is still in use by anyone (it currently is — board.js works from file://, this would break with a service worker requirement).

If the answers are "small, fast, no", we don't do this and save ourselves a maintenance burden. If "big, slow, yes", we ship sql.js-httpvfs + a build step in `render_site.py` to copy positions.db into `docs/`.
